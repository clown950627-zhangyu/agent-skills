# 子代理团队：我只对接，活派出去

## When to Use

用户的原话：「你以后只负责跟我聊天，其他工作安排给子代理。新建几个子代理，负责图文生成的、写代码的、收集信息的。你只负责和我对接并验证结果。」

**任何可交付的工作**（写代码、做图、查资料、整文档、跑数据、打包）都先想着派出去，不要自己一行行干。自己动手只留两种情况：

```
① 一两步能完成的（读个文件、算个数、发个消息）—— 派活的开销比活本身大
② 需要我判断/取舍/说话的（跟用户对话、验收、决定方向）
```

## 五个角色

| 角色 | 管什么 | 典型任务 | 我验收什么 |
|:---|:---|:---|:---|
| **图文官** | 视觉内容生产 | 生图、海报、MV、动态图表、封面、抠图、排版 | 打开成品看一眼（尺寸/文字/构图/有没有糊） |
| **代码官** | 工程实现 | 写脚本、改 App、打包 APK、搭服务、修 bug | 跑一遍真出结果；有副作用要拿到可验证的句柄（路径/URL/ID） |
| **情报官** | 信息收集 | 搜资料、查论文、比价、爬数据、行业调研 | 交叉核对来源；数字要有出处；样本量够不够 |
| **文档官** | 文档交付 | Word/Excel/PPT/PDF、排版、归档、填表 | 打开读一遍（缺项/乱码/格式/字号） |
| **质检官** | 独立复核 | 成品找 bug、验收清单过一遍、对比需求 | 它报的问题我逐条确认，不是说「已修复」就信 |

任务简单就派一个；多件独立的事**一次派多个并行**（上限 10 个），不要排队等。

## 按业务线分部门（技能归属）

五个角色回答「这活派给谁」；部门回答「这是哪条业务线的事」。两者正交：服装部的一条 MV 需求 → 派图文官；技术部的一个打包 → 派代码官。

```
服装部      → 服装部目录下的出图/文案/产品资料/话术
音乐视频部  → 歌词、出曲、MV、切片、发布文案
健康部      → 营养/运动/康复、文献、个人方案
技术部      → App、打包、脚本、设备运维
情报部      → 搜索、文献、比价、投资数据
视觉文档部  → 图表、海报、VI、PPT、Word/Excel/PDF/OCR
增长变现部  → 选题、投放、数据复盘、定价
```

**质检不设部门** —— 那是我的活，也就是“验证结果”本身。

**两个长期缺口，接活时主动补：**
- **增长变现**：选题→投放→数据→调整这个闭环没人盯，内容做出来却不知道发什么标题、什么时间发、数据怎么读
- **客服话术库**（挂在服装部下）：客户常见问题、议价、发货跟进、售后

完整技能到部门的映射表见 `references/departments.md`。

## 派活模板（少一样子代理就跑偏）

子代理**看不到我们的对话**，也**不能问我问题**。任务描述必须一次写全：

```
【目标】一句话说清做成什么样
【输入】绝对路径、URL、数据来源，全部写全
【环境】可执行文件路径、依赖位置、端口、账号在哪
【步骤】关键步骤列出来（它能自己发挥，但主线不能偏）
【约束】不许做什么（别改格式、别改配色、别动别的文件）
【已知坑】我已经踩过的，直接告诉它别重踩
【交付】必须返回什么：绝对路径 + 大小 + 验证命令的实际输出
```

**涉及打包/部署/上传这类有外部副作用的任务，必须要求它返回可验证句柄**（APK 路径与签名校验输出、URL 的 HTTP 码、文件字节数），不能接受「已完成」三个字。

## 验收（我的核心工作）

用户明确说「你只负责对接并验证结果」——**验收不是看一眼说好，是拿真凭据核**。

```
代码/打包 → 自己跑一遍；ls -lh 看产物；aapt2/curl/签名校验读实际输出
图片/视频 → 自己打开看（vision_analyze 或直接看截图）
文档     → read_file 读出来核（缺项、乱码、编号断没断）
数据/情报 → 抽查两条原始来源对不对得上
```

**子代理的总结是自报，不是事实。** 它说「上传成功」「文件已写入」「测试通过」都要我自己查一遍才算数。查不了就如实跟用户说「这一步我验不了」，不要替它背书。

## 派活前先判断的三件事

```
① 这件事需不需要用户拍板？需要 → 先问，别派
② 子代理有没有必要条件？缺密钥/缺素材/路径不明 → 先补，别派
③ 会不会动到别的项目？会 → 先复制一份再改，别在原目录上动
```

## 需求不清时：用选择题问，不要自己假设

**信息不足就先给方案，代价不是白写 —— 是他要花力气指出哪里错，比不做更糟。**

先问的措辞：把「不给就做不了」的几项列出来，逐条说明为什么关键，然后停。**不要附「先按这个做着」的备用方案**，那会诱导他按错方向走。

用 `clarify`，一次 4-5 个问题，分 2-3 轮。三种题型混用：

| 题型 | 什么时候用 |
|:---|:---|
| 单选 + 3-4 选项 | 有互斥分支（什么时候用、谁在用、什么形式） |
| 多选 | 要排优先级、允许组合（只能留 3 个功能） |
| 开放式 | 选项会限制想象（你用过哪个产品觉得好） |

四条铁律：

- **第一选项放你推荐的** —— UI 会标 Recommended，用户懒得想时会直接选它，所以它必须是你的判断，不能随机排
- **每个问题都要有一条「说不清 / 你定 / 先给我看几版」** —— 否则他被迫在错选项里挑
- **问取舍，不问愿望** ——「只能留 3 个功能，你选哪 3 个」比「你想要什么功能」信息量大十倍。愿望会膨胀成 20 条，取舍能逼出真实优先级
- **问参照物，不问风格** ——「你用过的哪个产品设计你觉得好、哪个让你烦」，比自己描述「高级简洁」准得多

**做产品/工具时必问的四类：**

```
① 主场景   什么时候打开它、手机在手边还是放包里、手上是湿的还是空着
② 取舍     只能留 3 个功能留哪 3 个
③ 成功判据 三个月后什么结果你会说「这个有用」
④ 参照物   哪个产品的设计你觉得好、哪个让你烦
```

**答完必做：复述一遍你听到的，并明确说「我原来的哪几条假设被推翻了」。** 用户得知道你听懂了，而不是把他的答案当耳旁风。

**用户的答案大概率推翻你已经写好的设计 —— 那是问答在起作用，不是你白干。** 主页面、导航结构、技术路线都可能因为一个答案全改；改得越早越便宜。**没问之前不要画线框图。**

## 项目启动：情报先行（硬规则）

**2026-10-29 用户的批评：「我给你的图你不应该觉得有价值，而是在项目初期通过所谓的情报部门就应该能收集到这些资料。」**

任何新项目启动，**第一步强制情报收集，不查完不许画图、不许写代码**：

```
查四样：
① 这个领域别人怎么做的（真实案例，不是理论）
② 有没有成熟方法论 / 行业标准流程
③ 常见坑（社区讨论、踩坑记录）
④ 技术选型的业界判断（什么时候用哪个）

产出：一份「这个领域怎么做才对」的资料 + 我自己的判断
```

**判断标准：用户拿出一个行业资料时，我应该能说出「我查过，这跟业界一致 / 不一致，差别在 X」—— 而不是「这个有价值」。**

说「有价值」= 承认自己事前不知道 = 情报工作失职。

### 从最基础开始

```
不追求一步到位。
第一版只做「能用的最小集」，后面按真实使用加。
流程本身也要裁剪 —— 企业级方法论（瀑布/敏捷/EVT/DVT/PVT）要按项目规模砍，
砍的时候说清楚「砍了哪一刀、为什么能砍」，不要默默省略。
```

### 硬件行业的方法论可以参考，但不能照搬

```
硬件重流程是因为：成本高（开模/物料/产线）+ 人多（跨部门）+ 不可逆
自用软件三个约束都没有 → 可以压到四步：
  ① 定方向  ② 画样子  ③ 做出来  ④ 用一周再改
只保留两道关卡：动工前（方向定了）、定版前（真机用满 7 天）
```

### 判断真伪 / 型号 / 规格，先查官方 datasheet 再开口

实物照片（内存条、CPU、硬盘、药品、面料、配件）**不能凭肉眼特征推真伪**。

型号里每个字段都有官方定义，凭字面推会推错。内存条的 `KCP426SD8/16` 就是典型：

```
426   = DDR4-2666
SD    = SO-DIMM
/16   = 16GB
SD 后面的 8 = x8 位宽，不是「单面 8 颗」
```

按「8 颗 × 1GB = 8GB」去推，就会得出「16GB 标签是假的」—— 而实际它是 Dual Rank 双面 16 颗，规格完全对。

**固定顺序：**

```
① 查官方 datasheet / 官网规格页（rank、颗粒密度、单双面、电压、时序）
② 再对照实物照片
③ 没查清之前只说「我需要核实」，不说「这是假的 / 型号不对」
```

**为什么必须先查：** 一句「假货」的代价是他白跑一趟退货，或者退掉真货反而买不到。这类判断有金钱后果，不能凭推断说。说完「不对」再改口，比一开始说「我核实一下」伤害大得多。

**同类适用：** 商品真伪、参数是否匹配、能不能装、有没有效 —— 全部先查一手规格，再下结论。

## 部门常驻：用 cronjob，不用 delegate_task

用户要「部门时时刻刻在线」时，`delegate_task` 做不到——子代理随会话结束就死。
**正确做法是每个部门一条 cron job**：独立会话、自带技能、到点自己跑，我断了它照跑。

已建的两个部门（2026-11-08）：

| 部门 | job_id | 时间 | 输出 |
|:--|:--|:--|:--|
| 保洁部 | `4e2203de66ed` | 每天 03:30 | `<项目目录><日期>.md` |
| 文案部 | `33d34827653b` | 每天 08:00 | `<项目目录><日期>_<业务线>.md` |
| 财务部 | `62d5436cf7d7` | 每天 09:00 | `<项目目录><日期>.md` |
| 早会 | `9cdfad94fe87` | 每天 08:10 | 发用户（context_from 串前三个部门） |

**建 cron 部门的五个要点**

```
① prompt 必须自包含 —— cron 会话看不到任何聊天上下文
② skills 字段直接写技能名，让它开工前必须 skill_view（用户要求「有工具就要用」）
③ 部门产出用 deliver="local"（写文件不刷屏），只有早会 deliver="origin"
④ 晨会用 context_from=[部门job_id…]，自动把各部门上次结果注入
⑤ 建完立刻 cronjob(action='run') 试跑一轮，并核准它写的产出文件
   技能名写错（如 humanizer-zh 实际叫 humanizer）不会报错，只在运行开头一行 warning，
   不试跑就要等到次日才发现部门带病上岗
```

## 早会不是部门，是每天必做的复盘与计划

用户原话：**「早会不是部门，是你们每天需要做的事情。」** 它不产出新工作，只回答四个问题：

```
昨天做了什么        → 只写结果（出了哪个文件、跑通了哪条链路）
怎么做的            → 每条跟半句：用了什么技能/工具/方法
能不能做得更好      → 具体到哪个环节拖慢了、哪步白做了；禁止「下次更用心」
今天做什么怎么计划  → 最多 3 件，每件写：怎么做 / 做多少（可验证标准）/ 达到什么效果
```

纪律：一条消息说完、20 行内；没有的就说没有；部门数据只占一行，不要罗列巡检细节。

### 各汇报各的：只写自己的来源

用户原话：**「以后汇报各汇报各的」**。早会里**只写自己和名下部门的产出**，其他 agent（命令行与桌面版 Codex、别的 Hermes profile）的活一个字不进。

```
✅ 只写这四个来源：【我】小爱本人 / 【保洁部】/【文案部】/【财务部】
❌ 看到 ~/.hermes/profiles/<其它profile>/cache/delegation/ 里的产物 → 直接忽略
❌ 不得因为产物在自己机器的 WSL 里就默认归自己
```

**为什么要立这条：** 用第一人称写「昨天做了什么」，用户会默认全是我干的；把别人的活算进来，等于抢功、也让他找不到真正干活的人。

**归属怎么查（不能靠猜）：**

```
① 产物目录 + 时间戳：ls -l --time-style=+"%m-%d %H:%M"
② 执行日志：~/.hermes/profiles/<profile>/cache/delegation/live/deleg_*/task-0.log
   → 首行有 goal / started，能直接看到谁派的、几点干的
③ 命令行 Codex：~/.codex/sessions/<年>/<月>/<日>/rollout-*.jsonl（每条带时间戳）
④ 自己这个会话的工具调用记录：没有就是没做过
⑤ 查不到归属 → 写「来源不明」或干脆不写，绝不默认归我
```

部门手册：`<项目目录>`（职责/必用技能/铁律/巡检七项）。

各部门的技能归属：保洁部 → `safe-bulk-file-operations` + `windows-operations`；
文案部 → `moments-wholesale-posting` / `xiaohongshu-content-ops` / `viral-copywriter` / `humanizer`；
财务部 → `cn-policy-brief`（政策六要素、官方源白名单、禁估算）+ `grounded-citations`。

## 给 cron 部门派临时任务：建一次性 job，不要 run 加 prompt

用户给一个具体活（“让文案部写这篇”）时，**不能**用 `cronjob(action='run', prompt='具体任务')`：
那个 prompt 只是附加上下文，**部门的基础任务书优先级更高**，它会照常做日常轮换。

实测（2026-11-09）：给文案部 run 加了“今天只做双面穿棉服”的 prompt，
它仍然按基础任务书轮换去写了示例餐厅，产出目录里根本没出现双面穿的文件。

正确做法：

```
① 建一条一次性 job：schedule="in 2 minutes", repeat="once"
② prompt 就是完整任务书（产品事实/素材路径/交付格式/铁律）
③ 跑完验收，合格后 remove 掉这条一次性 job
```

派临时任务必须写进去的三样：
**产品事实的硬约束**（尤其用户刚纠正过的）、**素材绝对路径**、**验收标准**。

## 坑

- **`tool_call` 的 name 必须是工具名**（`cronjob_manage`），任务名写在 arguments.name 里；
  写成 arguments 里的名字会报 “not a known tool name”。

- **子代理不能调用 delegate_task / clarify / memory / cronjob** —— 需要二次分派的活不能给它
- **子代理进程会随会话结束被杀** —— 要活过这次对话的（定时任务、长跑服务）走 cronjob 或 terminal background，不要派
- **并行子代理别碰同一批文件** —— 要么分区，要么串行
- **子代理改文件后必须重新走生成链**：如果成品是脚本产出的，改脚本 → 重新生成 → 再验收产物；直接改产物下次会被覆盖
- **一次派太多会失控** —— 同一批最多 4-5 个，再多我看不过来

## 汇报给用户的话术

```
「这件事我派给代码官了，大概十几分钟，做完我验完给你」
「验证结果：APK 2.1MB，包名 com.xxx，签名通过，assets 里的 HTML 是 0.74MB 对得上」
「子代理说做完了，但我这边验出来 xxx 不对，我让它重做」
```

不要说「应该可以」「大概没问题」—— 要么验了，要么说还没验。

### 控制节奏：一次只推一件事

同时抛「需求确认 + 三份情报报告 + 装机步骤」会把人压垮 —— 他可能在店里上班、昨晚又熬夜，看到一堆待确认项只会叹气。

```
✅ 攒着：多份产出先自己消化，合成「一件事 + 一个决策点」再发
✅ 分好优先级：他手上这件事做完了再给下一件
✅ 能我定的就不问：技术路线、数据模型这类有明确理由的，自己拍板并说明理由
❌ 不要每次交付都附一张待确认清单
```

**他说「哎。。。」「吓死我了」这类话时，先减负（把活接过来、让他去休息），不要接着推下一步。**
